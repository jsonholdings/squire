## Controlled load test: 6 concurrent calls, real 3-agent load present

`squire sum squire.py`, `squire sum README.md`, `squire sum CHANGELOG.md`, `squire triage <file>`,
`squire diff --staged`, `squire run -- find ... -name '*.py'` launched together as background
shell jobs. `diff --staged` had nothing staged (no model call, correctly skipped). One `triage`
invocation errored on a bad relative path in the test script itself (`FileNotFoundError`, never
reached the lock/model) — an operator error, not a squire defect.

5 calls reached the model concurrently:

| metric | p50 | p95 | max |
|---|---|---|---|
| queue_wait_s | 9.00 | ~28.7 | 30.27 |
| gen_s | 7.36 | ~12.4 | 13.32 |

Backend-ok: 5/5. Busy fast-fails (`queue_wait_s` hitting the 240s `LLM_LOCK_TIMEOUT`) across the
**entire ledger, all time**: **0**. GPU free at test time: 12,319 MiB (`nvidia-smi` via
`flatpak-spawn --host`, no room concern for `SQUIRE_MODEL=auto` upsizing, and no headroom reason
to downsize either).

## Tuning applied

**None.** The numbers don't justify one: queue waits under 6-way real concurrency (max 30.27s)
stay well inside the 240s lock timeout with no fast-fails anywhere in the ledger; gen_s (3.7–13.3s)
is in line with `qwen2.5:14b` at `num_ctx=16384` on this GPU, not context-bound enough to justify
trading it for a smaller model tier on sum/diff/triage. S1's client-side serialization (35d2b60)
is doing what it was built to do — disk (`df -h ~`: 292G free /home) was checked and is not a
blocker if a future measurement does justify a smaller model.
